# HWInfo — 后端采集层优化计划

> 版本：v1.0
> 日期：2026-10-19
> 范围：`core/` + `collectors/` + `utils/`（硬件信息采集后端）
> 基准：以当前代码实现为唯一事实来源（文档已同步对齐至本计划制定时的实现）

## 0. 现状评估

后端已具备完整的 9 大类采集能力，整体工程水位不错：

- 分层清晰，`utils/` 不依赖业务模块，`collectors/` 之间零耦合
- 性能意识强：注册表替代慢速 WMI 关联查询、pci.ids 懒加载、避开 `systeminfo` / `Win32_PnPSignedDriver`
- 容错完备：三级错误模型 + 整体超时兜底 + 逐级优雅降级
- 并发正确性有意识处理：WMI 线程本地连接 + 首次初始化竞态锁

主要短板集中在三处：

| 类别 | 表现 |
|------|------|
| **运行时健壮性** | 共享线程池的 `max_workers` 一次性固化；挂死的 WMI 调用会永久占用池槽位 |
| **数据准确性** | 大量启发式推断（SSD/HDD、通道模式、独显核显、指令集），无样本库与真机回归 |
| **一致性** | 需求文档与实现的偏差（超时策略、权限标注、多设备编号、厂商 ID 兜底第三级等） |

优化按「先止损、再提准、最后增强」三阶段推进。

## 阶段一：运行时健壮性（P0，改动小、收益高）

### 1.1 共享线程池的 `max_workers` 一次性固化

**问题**（`core/manager.py:21-28`）

```python
executor = _get_shared_executor(len(targets))  # 仅首次创建时生效
```

GUI 首次采集若因设置页只启用 3 个类别，池即被固化为 3 线程；之后用户恢复全部 9 类，采集会被分成 3 批串行执行。

> **2026-10 更新（GUI 改顺序采集后）：** GUI 已改为 `parallel=False`
> 顺序采集（原因见设计文档 §9.5），不再触碰共享线程池；CLI 每次进程只调用
> 一次 `collect()`，池容量天然匹配。**因此本项在现有调用路径下已不可达**，
> 保留作为防御性改进（例如日后出现「单进程多次并行采集」的调用方）。

**方案**：池容量取历史最大值，分类别集合变化不影响并发度。

```python
def _get_shared_executor(max_workers: int) -> ThreadPoolExecutor:
    global _executor
    if _executor is None:
        _executor = ThreadPoolExecutor(
            max_workers=max(8, max_workers),
            thread_name_prefix="hwinfo-collect",
        )
    return _executor
```

同时在 `CollectorManager.__init__` 记录 `_executor_size`，按需扩容（`ThreadPoolExecutor` 本身不支持扩容，故简化为「一次定型，取够用值」）。

**验收**：构造「先 3 类别、后 9 类别」的两次**并行**采集 → 观察第二次 `result.timings` 总耗时仍为并行量级。

### 1.2 挂死的 WMI 调用毒化共享线程池

**问题**（`core/manager.py:121-140`）

`as_completed` 整体超时后，future 被放弃但底层工作线程仍在阻塞。`cleanup_com()` 写在 `finally` 里，挂起时也执行不到。槽位被永久占用；池被占满后，后续 F5 刷新会全部排队等待。

> **2026-10 更新：** GUI 走顺序路径后不再使用并行池，「F5 刷新全部排队」的
> 场景随之消失；并发路径只剩 CLI（单进程一次采集）。本项同样降级为
> 防御性改进。

**方案（分两级）**

1. **软隔离**：为每个采集任务分配独立的「槽位租约」，整体超时后把该工作线程标记为不可复用（`ThreadPoolExecutor` 难以剔除单个 worker，故采用「超时即整体降级为新建独立池」的策略）。
2. **进程级兜底**：CLI 侧整体超时后直接以退出码 3 结束（GUI 已走顺序路径，不经过整体超时逻辑）。

**保守实现**（推荐先落地这一版，风险最低）：

```python
except FuturesTimeoutError:
    logger.error("并行采集整体超时(%ss)，重建线程池以隔离可能挂死的工作线程",
                 self.TIMEOUT + 5)
    # 放弃旧池（不 shutdown(wait=True)，避免阻塞退出），新建干净的池
    global _executor
    _executor = None
    ...
```

配合 `gui/main_window.py:closeEvent` 已有的「关闭时挂接线程结束回调自动补关」逻辑，挂起的工作线程在进程退出时被 OS 回收。

### 1.3 单模块 10s 超时未按模块生效

**问题**：需求文档要求「单个 Collector 超过 10 秒未返回则跳过」，实现上只有整体 15s 兜底（`TIMEOUT + 5`），没有 per-module 超时。

**说明**：WMI COM 调用一旦进入就无法安全取消（强行 `CoUninitialize` 会导致解释器崩溃），因此 per-module 超时只能做到「标记超时并放弃等待」，做不到「真正终止」。这正是当前实现的设计取舍。

**方案**：明确语义为**软超时**——

- 在 `CollectResult.timings` 中把超时模块的耗时记为 `TIMEOUT`（当前已实现）
- 新增 `CollectResult.timed_out: list[str]`，显式区分「超时」与「采集失败」
- 文档同步：把需求中的「单模块超时」改写为「单模块软超时（标记并放弃等待）+ 整体硬兜底」

> **2026-10 更新：** 整体兜底只在**并行**路径生效，而 GUI 已改为顺序采集，
> 因此 GUI 不会出现「采集超时」标记。设置页相应撤掉了「单模块超时」控件，
> 改为说明文案「顺序采集 · 逐类读取，完成一类即时刷新」；
> `gui/worker.py::CollectWorker` 保留 `timeout` 形参并加注释说明其不生效。

### 1.4 关闭时的 COM 清理路径

**现状**（`gui/app.py:20-34`）：`_suppress_com_noise()` 在 `app.exec()` 之后执行，重定向 stderr 到 devnull 抑制 pythoncom 在解释器关闭时的 "Win32 exception" 噪音。

**方案**：保持现状（已验证有效），仅补充注释说明「为什么不能放在 `sys.exit()` 内部」。

## 阶段二：数据准确性（P1）

### 2.1 CPU 指令集改为真实探测

**问题**（`collectors/cpu.py:64-91`）：对所有 `intel64` / `authenticamd` 一律追加 `AVX`、`AVX2`。

事实：AMD Bulldozer（2011）支持 AVX 但不支持 AVX2；Intel 13 代起支持 AVX-512；FMA / SHA 普遍缺失。

**方案（按成本分两级）**

| 级别 | 做法 | 成本 |
|------|------|------|
| L1 | 基于 `Identifier` 中的 Family/Model 查内置型号表 | 维护成本高，覆盖不全 |
| L2（推荐） | 通过 `ctypes` 调 `IsProcessorFeaturePresent` | 只能拿到少量标志位 |
| L3 | 走 CPUID 指令（`__cpuidex`）读叶子 1 的 ECX/EDX 与叶子 7 的 EBX | 需要 ctypes 机器码，最准确 |

L3 的 CPUID 实现约 80 行，可完整给出 SSE/SSSE3/SSE4.1/SSE4.2/AVX/AVX2/AVX-512/FMA/SHA/BMI2 等标志位，是彻底方案。

**过渡方案**：在 L3 落地前，至少修正注释与文档，明确标注「基于型号族的启发式推断，非精确探测」。

### 2.2 GPU 独显/核显判断的准确性

**问题**（`collectors/gpu.py:152-185`）：靠名称关键词 + `AdapterCompatibility` 厂商关键词组合判断，Intel Arc A770 会被误判为独显（`arc a7` 命中），AMD 核显在厂商信息缺失时默认判独显。

**方案**

1. 引入总线信息维度：读取 `PNPDeviceID` 中的 `PCI\VEN_xxxx` 结合 `pci.ids` 判定，核显通常挂在 CPU 厂商总线（`VEN_8086` / `VEN_1022`）且 `SUBSYS_` 为板载值
2. 用 `pci.ids` 设备名反查更完整的型号特征（pci.ids 里核显型号带 `Graphics` / `VGA` 后缀的规律明显强于 WMI 名称）
3. 保持「无法判定时输出『未知』」而非强行二选一

### 2.3 多 NVIDIA 显卡的 pynvml 数据错配

**问题**（`collectors/gpu.py:187-217`）：`nvmlDeviceGetHandleByIndex(i)` 的顺序与 WMI `Win32_VideoController` 列表顺序不保证一致，双 N 卡机器上负载/显存可能挂错卡。

**方案**：用 `nvmlDeviceGetPciInfo()` 取 `busId`（形如 `00000000:01:00.0`），与 WMI 侧 `PNPDeviceID` 中的 PCI 地址匹配后绑定；匹配不上时回退到当前按下标的方式并在字段上标注不确定性。

### 2.4 存储类型判定的关键词误伤

**问题**（`collectors/storage.py:128-157`）：`ssd_keywords` 含 `"p1"` / `"p3"` / `"p5"` / `"gx"` 等过短片段，误判概率不低。

**方案**

1. 关键词加词边界（正则 `\b` 或前后校验），去掉 2 字符的裸匹配
2. 引入 `MediaType` 兜底：Win32_DiskDrive 的 `MediaType` 字段在部分驱动上有效，可作为第一优先级
3. 保留关键词表作为最后兜底，命中策略时把该字段标为「推断值」

### 2.5 内存通道模式推断

**问题**（`collectors/memory.py:147-158`）：仅按条数推断，2 条一律「双通道」；实际在四通道主板上插 2 条属于单通道模式。

**方案**：读 `Win32_PhysicalMemory` 的 `DeviceLocator`（DIMM_A1/B1/C1/D1 等）推断通道归属——同一通道为 A/B 或 C/D，跨通道填充才是双通道。插槽名不可靠时回退到现有条数推断。

### 2.6 显示器 EDID 与 VideoController 的配对

**问题**（`collectors/monitor.py:36-40`）：EDID 列表与 VideoController 列表按索引配对，多显示器 + 含无输出核显时会错配。

**方案**：`WmiMonitorID` 本身带 `InstanceName`（含 `\\DISPLAY\GEN1\...`），可通过 `DisplayConfig` API 或注册表 `Enum\DISPLAY` 建立 EDID ↔ 输出路径的映射；映射不可靠时，只输出 EDID 自带信息（型号/厂商/年份/周），分辨率与刷新率置空而非猜测。

### 2.7 虚拟化状态的语义修正

**问题**（`collectors/cpu.py:93-121`）：降级分支读 `DeviceGuard\EnableVirtualizationBasedSecurity`，但 VBS 开启 ≠ VT-x 开启。

**方案**：降级分支改读 `HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity` 之外的正确键，或直接返回 `None` 并在 `_警告` 中说明「无法确定虚拟化状态」，不再用 VBS 近似。

## 阶段三：增强能力（P2）

### 3.1 采集结果缓存 / 差分

- 快照缓存：把上次采集结果落盘为 JSON，支持「对比上次」视图
- 需求文档 §第三阶段已规划「硬件变更对比（快照 diff）」，此项为其前置

### 3.2 温度与风扇（需内核驱动）

- 集成 LibreHardwareMonitor 做温度/风扇采集
- 属于新能力，不影响现有结构

### 3.3 磁盘健康信息（按需开关）

当前刻意不采集 `MediaType` / `HealthStatus`（PowerShell 启动固有开销 1.5~2s + 需管理员）。建议：

- 改为**配置开关** `collect.disk_health: auto | always | never`
- `auto`：仅在管理员模式下、且用户显式查看存储详情时采集
- 用 `Get-PhysicalDisk` / `Get-StorageReliabilityCounter` 一次拿全，避免多次 PowerShell 调用

### 3.4 厂商 ID 兜底第三级

需求文档 §2.3 写的是「pci.ids 也查不到时，显示原始 VEN/DEV ID」，当前实现是显示「未知显卡」。

**方案**：补上第三级，输出 `VEN_10DE&DEV_2782` 形式的原始 ID，便于用户反馈与检索。

### 3.5 多设备编号显示

需求文档 §2.9 要求 `[独显 0]` / `[磁盘 0]` / `[显示器 0]` 编号，当前终端格式化器用 `[类型] 名称` 代替（存储类会显示为 `[SSD] 型号`）。

**方案**：在 `formatters/terminal.py` 的 `_get_item_title` 中按类别生成编号前缀，与需求文档对齐。

## 原则约束

优化过程中必须保持以下不变量：

1. **采集与展示分离** —— Collector 只产出 dict，Formatter 只渲染
2. **`collectors/` 之间零依赖** —— 新增共享逻辑一律下沉到 `utils/`
3. **中文键名 dict** —— 不引入 dataclass 改造数据结构
4. **单模块失败不影响整体** —— 任何新增采集点都不得抛出未捕获异常
5. **不写日志文件** —— 日志只到 stderr
6. **字段不丢失** —— 任何重构以真机 JSON 快照 diff 为第一验收标准
